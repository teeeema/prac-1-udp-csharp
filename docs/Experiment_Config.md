# Experiment Config

## Environment

| Параметр | Фактическая опора |
|---|---|
| Приложения | UdpGame.Server и UdpGame.Client, режим --experiment |
| Runtime / target | .NET 10, TargetFramework = net10.0 во всех проектах |
| Точная версия SDK/runtime сохранённого запуска | Не записана в CSV; по исходникам не восстанавливается |
| OS сохранённого запуска | Не записана в CSV и не определяется исходниками |
| Address | 127.0.0.1 (localhost), значение по умолчанию ClientOptions |
| Port | 27015/UDP, значение по умолчанию клиента и сервера |
| Bind сервера | UdpTransport.Bind: UdpClient(port), IPv4 any |
| Источник результатов | [latency_samples.csv](latency_samples.csv) |

CSV не содержит host, port, OS, календарную дату или сведения о машине. Адрес и порт выше описывают предусмотренную кодом localhost-конфигурацию; подтвердить фактические CLI-аргументы исторического запуска только по CSV невозможно. Указанная в прежней документации точная версия macOS не имела такого подтверждения и здесь не приписывается эксперименту.

Серии выполняются последовательно. Для каждой создаются новые tracker, transport и Random. Следующая плановая отправка вычисляется от начала серии с шагом 200 ms; фактические моменты доступны в sent_at_ms. Измерение начинается до сериализации PING и решения эмулятора, поэтому искусственная задержка входит в RTT.

## Профили Network Emulator

| experiment_id | Base delay, ms | Jitter, ms | Вероятность loss | Итоговая задержка не удалённого PING, ms |
|---|---:|---:|---:|---:|
| baseline | 0 | 0 | 0% | 0 |
| delay_50 | 50 | 0 | 0% | 50 |
| delay_100 | 100 | 0 | 0% | 100 |
| jitter | 0 | 50–150 | 0% | 50–150 |
| loss_5 | 0 | 0 | 5% | 0 |
| combined | 100 | 50–150 | 5% | 150–250 |

Эмуляция программная, внутри UdpTransport.Send экспериментального клиента. NextDouble() × 100 < LossPercent определяет удаление при ненулевом loss. Jitter выбирается Random.Next(min, max + 1): целое число, обе границы включены. Решение содержит BaseDelayMs + jitter; удалённый пакет не отправляется, задержанный отправляется через Task.Delay. Серверный SendTo и приём не эмулируются; системные сетевые утилиты для этих профилей кодом не вызываются.

## Критерий timeout

Expire помечает Pending как Timeout при nowUs − SendTimeUs >= 1 000 000 µs. Проверка выполняется в начале итерации, поэтому запись появляется при ближайшем вызове Expire, а не строго в момент истечения таймера.

RecordPong не проверяет дедлайн самостоятельно: после уже установленного Timeout возвращается LateResponse. Для ещё Pending ответ принимается как Received. Это граница текущей реализации, а не обещание точного срабатывания на 1000.000 ms. Сокетный timeout 1–20 ms только возвращает управление циклу.

## Воспроизводимость

Фиксированный seed воспроизводит решения эмулятора при одинаковых профиле, реализации Random и порядке вызовов. Он не фиксирует планирование ОС, фактический RTT, сетевую обработку или загрузку машины. В loss_5 и combined последовательности удалений различаются из-за дополнительных обращений к Random для jitter. Вероятность 5% не задаёт точное число удалений в выборке 50.

--count, --interval-ms и --timeout-ms относятся к обычному клиенту и не меняют константы ExperimentRunner. Host, port и путь --csv передаются эксперименту. Команды приведены в [README](../README.md); сохранённые результаты при подготовке этой документации повторно не измерялись.

## CSV

| Поле | Смысл |
|---|---|
| experiment_id | Название профиля |
| sample | Номер измерения 1–50 внутри серии |
| sequence | Сквозной SequenceNumber 1–300 |
| sent_at_ms | Время регистрации PING относительно старта эксперимента |
| rtt_ms | RTT успешного ответа; пусто при timeout |
| srtt_ms | SRTT при завершении записи; timeout не обновляет сглаживание |
| status | received или timeout |

WriteCsv сортирует строки по sequence, использует десятичную точку и три знака после неё. Он перезаписывает файл назначения. Для будущих запусков следует выбирать отдельный путь CSV, чтобы сохранить исходный набор результатов.
